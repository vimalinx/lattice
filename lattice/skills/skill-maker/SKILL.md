# 先判断归谁
学习者说「以后都这样」时，先分清这句话该落在哪：
- 关于学习者本人、换个主题也成立的（会什么、怎么学最顺）→ 用 remember 记下，不写成技能。
- 某一个 AI 每一轮都要守的做事方式（回复的长短、先给结论再展开）→ 用 rules_edit 改那个 AI 的规则。
- 一类任务的完整做法（怎么引入新概念、怎么读论文、怎么排计划）→ 技能。

# 动手前：看清分工
1. 用 list（kind=skills）列出全部技能，挑出 description 和这件事沾边的几个，用 skill 读全文。
2. 决定改还是建：
   - 已有技能管这件事 → 改它，不新建。
   - 两个技能都声称管同一种情形 → 改它们的 description，定下哪个先上、另一个什么时候接手；重复的做法只留一处，另一处写「照『某某』做」。
   - 确实没有技能管 → 新建。
3. 检验分工：想两三句学习者真会说的话，逐句问「这句话会让哪个技能被选中」。每句都应该只有一个技能先被选中。

# 写好一个技能
- **description 就是触发条件。** AI 只凭这一句决定用不用，所以写具体情形和学习者会说的原话；和邻近技能容易混的，加一句「……时不用，用『某某』」。不写它有多好。
  例（分工清楚的一对）：「论文精读」写「学习者要读懂一篇论文时……」；「主题调研」写「要了解一个陌生领域的全貌时……」。只读一篇论文的请求只会选中前者。
- **正文结构**：什么时候用（和什么时候不用）→ 要做到的（能检验的结果）→ 做法（编号步骤，每步说清用哪个工具、产出放在哪）→ 和其他技能怎么配（只写名字，不抄它们的做法）→ 不要（真出过的错）。
- **短。** 正文一千五百字以内，越短越好。长的模板、清单、例子放成附带文件，正文里写「照附带的 xx.md」。
- **一个完整的小例子胜过十条规则。** 能让 AI 从几个选项里挑的，就不要让它自由发挥。
- agents 只留真会用它的 AI（tutor 主会话、flash 快答、coach 练习教练、organizer 整理）；category 从「讲解思路 / 课程与教程 / 练习与评估 / 复杂生产 / 研究与阅读 / 笔记与整理 / 其他」里选。
- 不写一次性的具体内容（某个主题的路线、某次对话的细节）；技能是反复用的做法。

# 改一个技能
- **有证据再改。** 说清是哪次对话、哪一步出了什么问题（用 conversation、journal 找出来），在 why 里一句话写明。只凭感觉不改。
- **从现在的全文改。** 先用 skill 读它现在的全文：学习库里的版本可能带着学习者批准过的修改，不要拿商城原版覆盖，也不要顺手重写没出问题的部分。小改用 edits。
- **附带文件一起看。** 正文引用的模板、清单跟着改，删掉不再用的引用。
- **不动 version。** 它是商城用来提示「有新版本」的，学习库里改技能不用改它。

# 提出
- 用 skill_edit 提出，不要用 write 或 edit。新建时 new 为 true，content 是完整的 SKILL.md，开头的属性要有 name（英文短名）、title、description、category、agents。
- questions 给两三句学习者真会说的话，要能让改前改后两版答得不一样；学习者点一句就能对比两版。
- 回复里说清：改了哪个、为什么，以及和哪几个技能的分工变了。

# 不要
- 不要为一件已有技能管的事再建一个。
- 不要让两个技能的 description 都能匹配同一句话，却不说哪个先。
- 不要把别的技能的做法抄进来；写名字，让 AI 去读。
